# Reviewing PRs / Contributions to an MCP Server

Use this when the user asks you to review a contributor's PR, patch, or proposed changes to an existing MCP server — especially one billed as a "security fix" or "hardening" PR. These are exactly the PRs most likely to smuggle in unrelated changes, because reviewers relax scrutiny once they see the word "security."

## Scope check (do this first, before reading a single diff line)

1. **Restate what the PR claims to do**, from its title/description, in one sentence.
2. **List every file it touches.** For each file, ask: does this belong to the claimed scope?
3. **Flag anything outside scope explicitly**, even if it looks like a good idea on its own:
   - New dependencies or subsystems not mentioned in the PR description (a bundled dashboard, a new HTTP server, a new package) — these need their own review and their own PR, not a ride-along.
   - Deleted files, especially `CONTRIBUTING.md`, `.gitattributes`, CI config, or license files — deletions in a "fix" PR are a red flag almost by default.
   - Changes to build output / bundled artifacts (`dist/*`, `*.bundle.*`, generated files) — these should never hand-change in a source PR; they're supposed to be regenerated by the build, and a hand-edit here can hide anything.
   - Changes to install/postinstall scripts — verify they're still pinned (exact versions, checksums) and don't fetch-and-execute from a new URL.
4. **If scope creep is present, say so explicitly to the user and recommend splitting the PR** — don't silently accept the whole bundle because the core fix is good, and don't silently strip the extra parts yourself without flagging it.

## Security-specific checks, once scope is confirmed

- **SQL/query safety**: every dynamic value goes through parameterization; every dynamic identifier (table/column name) is validated against a live allow-list, not string-matched or regex-filtered.
- **No hand-rolled SQL parsers as a security boundary.** If the PR adds or modifies a parser meant to detect/block dangerous statements, treat that as at best a UX hint — check whether the real boundary (DB role privileges) exists and is unchanged or improved. A "SQL parser rewrite" that isn't paired with role-level restriction hasn't actually fixed anything.
- **Error messages**: confirm production-path errors don't leak connection strings, stack traces, internal hostnames, or full query text.
- **Cross-platform paths**: if the PR touches anything path-related (e.g., `pg_dump` invocation, file writes), check it doesn't hardcode POSIX-style paths — Windows path handling bugs are a common "worked on my machine" issue in DB-tooling PRs.
- **Cache invalidation**: if the PR adds or changes a schema cache, confirm there's an invalidation path, not just a TTL bolted on.
- **Install script pinning**: exact versions/checksums, no `curl | sh`-style fetch-and-execute additions.

## Communicating the review back to the user

Structure it as: (1) does the core claimed fix look correct, (2) what's out of scope and should be split out, (3) any remaining security gaps even within the claimed scope. Don't bury the scope-creep finding at the end — it's often the more important finding for the maintainer to act on quickly (e.g., telling contributors up front "please don't bundle unrelated changes into security PRs, resubmit split").
